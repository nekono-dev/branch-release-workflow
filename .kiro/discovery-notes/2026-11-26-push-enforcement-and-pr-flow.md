# discovery の結論: 終了時の未 push の防止と、分岐元からの PR・PR 経由のマージ（BRW）

2026-11-26 の `/kiro-discovery` の結論。経路は **Path A（既存の仕様の拡張。新しい仕様は作らない）**。入力は次の 3 つ。

- 利用者の指摘: `kiro-discovery`・`kiro-spec-init` を実行すると作業ブランチは作られるが、push までは強要できていない。
- 未マージの `origin/dev/checkpoint-push-rule`: `brw-enforcement` の要件 2 の 9〜16 の下書き（要件の文面のみ。承認は取り消し済み）。この作業ブランチに取り込み済み。
- 引き継ぎメモ [2026-11-26-pr-to-protected-and-merge-pr.md](2026-11-26-pr-to-protected-and-merge-pr.md)（分岐元から保護ブランチへの PR、PR 経由のマージ）。

## 利用者が決めたこと

1. 範囲は 3 件すべて（push の強要・分岐元からの PR 作成・PR 経由のマージ）。
2. push の強要は「応答を終えようとしたときに止める仕組み（Stop フック）」と「区切りごとの手順書」で行う。
3. **目的は「作業を終えようとしたとき、未 push の作業ブランチが残らない」こと。** 区切りごとの commit・push は、その手前で作業が失われないようにする補助とする。
4. **BRW は cc-sdd（kiro 系の仕様駆動の手順）を知らない前提。** 要件・設計・手順書の文面に `spec`・`kiro`・`cc-sdd` などの語を使わず、「文書や成果物のまとまりの作成完了」「実装の 1 つの作業単位の完了」のような一般の言い方にする。
5. 下書きの要件（brw-enforcement の要件 2 の 9〜16）は取り込んで続ける。
6. PR 経由のマージは、分岐元向けの PR だけを、利用者の確認つきで許可する。**保護ブランチ（`main`）向けの PR のマージは禁止のまま。** 利用者の確認とは、エージェントが代行できない承認（利用者が自分で承認する・自分の端末で実行する）を指す。

## 既存の仕様ごとの変更

### brw-enforcement（要件の見直しからやり直し）

- 要件 2 の 9・10 は「spec の要件・設計・タスク」と書いてあり、cc-sdd の語が入っている。決定 4 に従い、一般の言い方に直す。
- 要件 2 の 12（未 push があれば応答の終了を止める）を中心に据える。現在の Stop フック（`scripts/agent-hooks.mjs` の `stopGuidance`）は「準備済みで未公開の作業」しか止めない。未コミットの変更・未 push の commit も検出して止める形に広げる。Claude と Codex の両方で同じ判定にする（Codex は `brw guard` 経由の確認も含む）。
- 要件 2 の 14（push を禁じる指示があるときは止めない）・16（保護ブランチなどでは適用しない）は、無限に止め続けない条件（同じ応答で繰り返し止めない）を設計で決める。
- 要件 3 の 3（保護対象の分岐元への PR を用意したら、マージは利用者が行う）を、「分岐元向けの PR は、利用者の確認があれば、マージの操作を禁止しない」に直す。保護ブランチ向けのマージの禁止は変えない。確認の仕組みは `--confirmed` など既存の承認の扱いに合わせる。設計の段階で、確認をどう検証するか（エージェントが代行できない形）を決める。
- spec.json の承認は取り消した状態（requirements-generated・未承認）。要件の更新後に、設計・タスクも更新する。

### brw-pr-handoff（要件 1 の拡張）

- 分岐元（`develop` など）から保護ブランチ（`main`）への PR を、`brw pr` で作れるようにする。現状は `brw work start` が分岐元を拒否し、`brw pr-template` が「開発ブランチではない」と終了し、直接の `gh pr create` も拒否されるため、行き止まりになる。
- 要件 1 の 4（現在のブランチが開発ブランチでないと PR を作らない）を、「分岐元から保護ブランチへの PR は例外として作れる」に直す。マージは作らない（PR の作成のみ）。
- 拒否の案内が「`brw pr` を使え」と言うのに、`brw pr` が受け付けない行き止まりを無くす。
