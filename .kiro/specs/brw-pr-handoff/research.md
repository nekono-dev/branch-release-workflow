# 調査記録: brw-pr-handoff（設計前の検証）

検証日: 2026-11-25。環境: Claude Code 2.1.329、Node.js 22。使い捨ての Git リポジトリと、既存の `scripts/` の読み取りで確かめた。

## 検証結果

| # | 確かめたこと | 結果 | 設計への影響 |
|---|---|---|---|
| 1 | 片付けで作業ディレクトリ（worktree）が消えた後、Claude Code の Bash の作業場所はどうなるか | 次の Bash 呼び出しで、**起動時のディレクトリへ自動で戻る**（消えた場所でのコマンドは失敗するが、その次から復帰）。`cd` の強制は不要 | 片付けは worktree の中から実行してよい。案内は「リポジトリ本体のパス」と「次の `brw create`」で足りる。同じコマンド内で消した後の `pwd` などは失敗しうるので、片付けは publish の最後に行い、後続のコマンドを続けない |

## 設計で確定する方針（検証に基づく）

- 片付けの順序: push → PR 作成 → 作業状態を `published` にする → `finishBlocker` で確認 → worktree とローカルブランチを削除 → 状態ファイルを削除 → 案内の出力。片付けが止まったら、PR は作成済みのまま理由を報告し、再試行できるようにする。
- 既存 PR を再利用した場合も、`finishBlocker` の判定に任せる（push 済みで PR があれば片付ける）。
- `brw pr` が作業 ID なしで呼ばれたときは、現在のブランチの作業を探し、無ければ作業を新規に記録して進める（`brw publish` の入力を補う）。

## 決定事項

- 未追跡ファイルの別コミット化: `.gitignore` の対象は元から含めない。エージェントが止められない場合に備え、秘密らしい名前の接頭辞・パターンの一覧（`.env`・`*.pem`・`*credentials*` など）に当たるファイルが含まれるときは、含めずに publish を止める（防御の多重化）。
- 別コミットのメッセージ形式の既定: `chore: 作業外の変更（ボーイスカウト）`。含めたファイルの一覧を本文へ書く。
- 作業状態: 片付けで状態ファイルを削除する（履歴は PR が持つ）。削除は worktree とブランチの削除が成功した後だけ行い、片付けが止まったときは残して再試行できるようにする。片付けを経ない孤児の状態ファイルは今回の対象外とする。

## 統合の判断（Synthesis）

- **一般化**: 片付けは `brw finish`（手動）と `brw pr` の最後（自動）で同じ処理。安全確認（`finishBlocker`）と削除（`removeBranch`）を `cleanup.mjs` に出して共有する。自動側は「PR は今作った」という事実を渡し、`gh` の検索に依存しない。
- **Build vs Adopt**: 承認・計画・状態記録は既存の公開（`publish.mjs`）をそのまま使う。本文の雛形は、GitHub が標準で読む `.github/PULL_REQUEST_TEMPLATE.md` を優先して採用する。ラッパーは新しい仕組みを持たず、既存の段階を呼ぶだけ。
- **単純化**: 設定は 1 キー（`afterPublish.cleanup`）と言語の 1 キー（`pullRequest.language`）だけ。別コミットの対象は 1 種類（未コミットの変更すべて）で、秘密らしい名前だけを除外・停止の条件にする。本文の自動生成は作らない。

## 3. 実装の選択肢

- **案 P1: 既存の流れ（作業の記録・準備・計画・公開）を拡張する。** 取り込み元の分類に「分岐元」を許し、公開の種類に「push なしの PR」を足す。`brw work start` が分岐元でも作業の記録を作れるようにする。 規模: 大。 リスク: 5 か所の前提を同時に変えるため、既存の開発ブランチの流れを壊さない試験が多く要る。
- **案 P2: 分岐元専用の軽い経路を `brw pr` の中に作る。** 作業の記録を作らず、事前確認 → 本文の確認 → 差の判定 → PR の作成（承認つき）を直接行う。既存の流れへの影響が小さい。 規模: 中。 リスク: 「同じ計画・承認・状態記録」（要件 1 の 8）とずれる。状態の記録が無いため、再実行時の既存 PR の再利用だけで冪等性を保つことになる。要件の文言の調整が要る可能性。
- **案 P3: 共通の判定（上の 1）だけ先に直し、手順を段階的に開く。** まず直接の PR 作成の拒否の案内を実行できる形（受け付けられない組には手作業の手順）にして行き止まりを無くし、続けて P1 または P2 を入れる。 規模: 小〜大の分割。
- 推奨の傾向: P3 で段階を分け、本体は P2（影響範囲が小さい）を基本に、要件 1 の 8 の「記録」をどこまで求めるかを設計で確定する。

## 5. 設計の前に確かめること（実現性の記録に反映する）

1. 実リポジトリで、`develop` から `main` への PR を GitHub の API で作れ、差が無いときの応答（作成できない）も確かめる。
2. ローカルの分岐元がリモートより先行しているかを、fetch の有無で正しく判定できる方法（`git rev-list`・GitHub の比較 API）。
3. `brw pr` の分岐元からの実行で、作業の記録なしに承認・PR 作成・再実行の冪等性が成り立つか。
4. 分岐元が本体のチェックアウトで、片付け（`finishUp`）が確実に通らないこと。
5. フックの `brw pr` の許可（`agent-hooks.mjs` 179 行の信頼済みコマンド判定）が、分岐元からの実行でも通るか。

# 設計の記録（2026-11-26）: 要件 1.8〜1.11・2.8・3.10・4.12

発見の種別は「既存の拡張」（軽い発見）。実機で確かめた内容は `feasibility.md` と `poc/` に置く。

## 決めたこと（根拠つき）

- **分岐元専用の軽い経路 `base-pr`（案 P2）を `brw pr` の中に置く。** 利用者の決定: 作業の記録は作業ブランチにだけ適用し、分岐元の PR は「リモートの取り込み → PR の作成 → 報告」の 3 段だけ。既存の公開（準備・計画・push）を分岐元へ広げると、5 か所の「開発ブランチだけ」の前提を同時に緩めることになり、片付けが分岐元に走る危険もある。
- 変える箇所は、直接の PR 作成の判定（`evalPrCreateRules`）、`brw pr` の事前確認の振り分け、`brw pr-template`、`brw work start` の案内文だけ。公開の準備・計画・push（`publish.mjs`）は変えない。
- **PR の作成・再利用の関数を `publish-pr.mjs` から切り出して公開する**（`createOrReusePr`）。作業の記録に依存しない形に分け、`runPublishPr` もこれを使う。リスク: 切り出しで既存の挙動を変えないこと（既存の試験で固定する）。
- 拒否の案内は組ごとに選ぶ。`brw pr` で作れない組には、作成画面の URL（通信なしで作れる）を含めた手作業の手順を示す。

## 簡素化・汎用化（design synthesis）

- 「差があるか」は、fetch 後のローカルの参照で足りる（`git rev-list --count origin/<保護>..origin/<分岐元>`）。GitHub の比較 API は使わない（通信と認証を増やさない）。
- 先行の検出は `ff-only` に任せられない（PoC）。`rev-list --count origin/<分岐元>..<分岐元>` を別に使う。

## 参照した資料

- GitHub REST API の記述（`github/rest-api-description`、`api.github.com.json`、`info.version` 1.1.4。取得 2026-11-26）: `POST /repos/{owner}/{repo}/pulls` は 201・403・422 を返す。
- 実 GitHub の読み取り（2026-11-26）: `gh api repos/nekono-dev/branch-release-workflow/pulls/12` が `base.ref=main`・`head.ref=dev/sync-base-branch`・`merged=true` を返し、BRW 経由の開発ブランチ→保護ブランチの PR が実在する。同じ API の `compare/main...main` は `status=identical`・`ahead_by=0`。
