# 要件定義書

## 概要

BRW 導入済みのリポジトリで Claude Code または Codex を使う開発者が、クラウドセッションや他のプロバイダでの作業によってリモートだけが進んだとき、手元の基底ブランチと作業ブランチを、リモートの最新に追いつかせられるようにする。現状は、エージェントによる `git pull` と `git merge` の取り込みが、取り込み先・取り込み元が開発ブランチでない限り一律に拒否される。そのため、基底ブランチ（`main` など）を手元で更新できず、既存の作業ブランチへ基底の変更を取り込む安全な手段もない。経緯と範囲は [brief.md](brief.md) に記録している。

## 境界の文脈

- **対象**　基底・保護ブランチの fast-forward に限る更新、開発ブランチへの基底・保護ブランチの取り込み、許可しない取り込みの拒否と案内、許可した取り込みの確認の省略、Claude Code・Codex・`brw guard` での同一の判定。
- **対象外**　`rebase` による取り込み、専用コマンド（`brw sync` など）の新設、分岐元・保護ブランチへの直接 commit・push の拒否の変更、GitHub 側の設定（Ruleset）、プラグインの導入状態の検査。
- **関連する運用**　恒常的な分岐元・保護ブランチ・開発ブランチの意味は brw-enforcement に従う。取り込み元として許可するリモートは `origin` だけとし、その追跡ブランチ（`origin/main` など）を指す。「fast-forward」は、手元の履歴の先端を、取り込み元の履歴の先へ、マージコミットを作らずに進める更新を指す。
- **隣接する仕様への期待**　brw-enforcement 要件 3-2「開発ブランチ以外を対象にしたマージの拒否」に対し、本仕様が要件 1・2 の範囲で例外を加える。brw-enforcement の承認済みの文書は書き換えない。それ以外の拒否（GitHub 上のマージと自動マージ予約の拒否を含む）は変えない。

## 要件

### 1. 基底・保護ブランチを fast-forward で更新する

**目的**　開発者として、手元の基底・保護ブランチを、履歴を汚さずにリモートの最新へ追いつかせたい。これにより、古い基底ブランチを起点にした作業や、古い状態での比較を避けられる。

#### 受け入れ条件

1. When エージェントが恒常的な分岐元または保護ブランチを取り込み先とし、`origin` の同名の追跡ブランチ（`origin/main` など）を取り込み元として、手元のブランチを fast-forward だけで更新するとき, the BRW shall 実行を拒否しない。対象は、手元のブランチを確認した状態での `git pull`・`git merge` による更新を含み、fast-forward に限られることが操作の形から保証されている場合（`--ff-only` の指定、または同等の設定）に限る。
2. When エージェントが作業ブランチの作業ツリーなど、更新対象のブランチを確認していない場所から、`git fetch origin <基底ブランチ>:<同名のブランチ>` で手元の基底・保護ブランチの先端を fast-forward だけで進めるとき, the BRW shall 実行を拒否しない。
3. If 手元の基底・保護ブランチと取り込み元の履歴が分岐していて fast-forward だけでは完了しないと、実行前に確認できるとき, then the BRW shall 実行を拒否し、拒否の理由と、PR による反映または開発ブランチ間のローカルマージという代替手段を表示する。
4. If fast-forward に限られることが操作の形から保証されていない更新（`--ff-only` の指定がない `git pull` など）であるとき, then the BRW shall 実行を拒否し、保証が付く形で再実行する案内を表示する。実行前に分岐を確認できない更新（取得前の `git pull`・`git fetch`）は、保証が付いた形に限って許可し、分岐していれば更新されずに終わるようにする。
5. If 更新が強制（`+` を付けた更新など）、マージコミットの作成（`--no-ff`）、または `rebase` を伴う指定を含むとき, then the BRW shall 本要件の許可を適用せず、従来の判定のとおり実行を拒否する。
6. If 取り込み先・取り込み元・更新先のいずれかを確定できないとき, then the BRW shall 更新を止め、確定できなかった理由を表示する。

### 2. 開発ブランチへ基底・保護ブランチの変更を取り込む

**目的**　開発者として、作業が長引いて基底ブランチが進んだ後、またはクラウドセッションなど別の場所で基底が進んだ後に、既存の作業ブランチへその変更を取り込みたい。これにより、古い基底を前提にしたまま作業や PR を進めずに済む。

#### 受け入れ条件

1. When エージェントが宣言上の開発ブランチを取り込み先とし、`origin` の追跡ブランチのうち、宣言上の恒常的な分岐元または保護ブランチに当たるもの（`origin/main` など）を取り込み元として、手元で取り込むとき, the BRW shall 実行を拒否しない。対象は `git merge origin/main` と `git pull origin main` を含む。
2. When 取り込みにマージコミットの作成が必要であるとき, the BRW shall 開発ブランチへの取り込みに限り、マージコミットの作成を理由に拒否しない。
3. If 取り込み先が宣言上の開発ブランチでない、または宣言外のブランチであるとき, then the BRW shall 本要件の許可を適用せず、従来の判定のとおり実行を拒否する。
4. If 取り込みが `rebase` を伴うとき, then the BRW shall 本要件の許可を適用しない。

### 3. 許可しない取り込みを拒否し、代替手段を案内する

**目的**　開発者として、許可されない取り込みがなぜ拒否されたのかと、代わりに何をすればよいかをその場で知りたい。これにより、判断を止めずに作業を続けられる。

#### 受け入れ条件

1. When エージェントが、要件 1・2 の許可に当たらない取り込みを試みたとき（手元の別ブランチ、`origin` 以外のリモート、宣言外のブランチを取り込み元とする場合を含む）, the BRW shall 従来どおり実行を拒否する。
2. When 取り込みを拒否するとき, the BRW shall 拒否の理由、対象のブランチ、および代替手段（PR による反映、開発ブランチ間のローカルマージ、基底ブランチの fast-forward 更新）を表示する。
3. When 同じ取り込みを同じ状態で判定するとき, the BRW shall 同じ判定結果と同じ案内を返す。
4. If `git pull` の更新元の指定が `<元>:<先>` の形（取得したものを手元の別のブランチへ書き込む形）を含むとき, then the BRW shall 取り込み元が開発ブランチ・基底・保護ブランチのいずれであっても確認を省略せず、実行を拒否し、手元のブランチを書き換える取り込みは許可しない旨と、代替手段（`git pull <リモート> <ブランチ>` の形、基底ブランチの fast-forward 更新）を表示する。

### 4. 許可した取り込みの確認を省略する

**目的**　開発者として、許可された取り込みのたびに確認を繰り返さずに進めたい。これにより、リモートに追いつく操作を負担なく行える。

#### 受け入れ条件

1. While 運用の宣言が登録済みである, when エージェントが要件 1・2 で許可した取り込みを行うとき, the BRW shall 操作ごとの追加確認を省略できるようにする。
2. While 運用の宣言が未登録または編集中である, when エージェントが要件 1・2 で許可した取り込みを行うとき, the BRW shall 確認を省略せず、ホストの通常の承認に任せる。
3. When 取り込み元の指定がなく、取り込みの対象を確定できない操作（`--abort` など）が行われるとき, the BRW shall 確認を省略しない。

### 5. Claude Code と Codex で同じ判定にする

**目的**　開発者として、利用するエージェントにかかわらず同じ取り込みの規則で作業したい。これにより、作業を別のエージェントへ引き継いでも挙動が変わらない。

#### 受け入れ条件

1. When Claude Code のフック、Codex のフック、または Codex の事前確認手順（`brw guard`）が取り込み操作を判定するとき, the BRW shall 同じ入力に対して同じ許可・拒否と同じ案内を返す。
2. Where Codex のフックが無効または未信頼である環境, the BRW shall `brw guard` による事前確認で、要件 1・2・3 の判定を同じ結果で返す。
3. Where BRW を導入していないリポジトリ, the BRW shall 通常のエージェント操作を通し、本仕様の判定を適用しない。

### 6. 既存の規則を変えない

**目的**　運用担当者として、今回の許可が他の保護の規則を弱めないことを確かめたい。これにより、基底ブランチの保護を保ったまま追従の不便だけを解消できる。

#### 受け入れ条件

1. The BRW shall 要件 1・2 の許可の対象を取り込みに限り、分岐元・保護ブランチへの直接の commit・push の拒否を変更しない。
2. The BRW shall 開発ブランチ間のローカルマージの扱い、および GitHub 上のマージと自動マージ予約の拒否を変更しない。ただし要件 3-4 に当たる `<元>:<先>` の形の `git pull` は、取り込み元が開発ブランチでも拒否する。
3. The BRW shall 照会だけの操作（`git fetch` による追跡ブランチの更新など、手元のブランチを動かさないもの）の扱いを変更しない。
4. When 手元のブランチの先端を動かしうる `git fetch` が要件 1-2 に当たらないとき, the BRW shall 従来どおり照会として通さない。
