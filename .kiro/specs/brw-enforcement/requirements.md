# 要件定義書

## 概要

BRW 導入リポジトリで Claude Code と Codex を使う開発者が、ブランチの用意からレビュー依頼まで同じ運用で作業できるようにする。現状は Claude Code のフックが Bash の commit・push を判定し、Codex の事前判定や作業完了後の手順は主に文章指示に依存している。両エージェントで操作を機械的に判定し、利用者（管理者）が導入時に求めた場合に限り GitHub 側でも分岐元への取り込みを制御する（GitHub 側の強制は既定 off の任意の追加事項で、BRW の本分ではない）。経緯と実行環境ごとの制約は [brief.md](brief.md) に記録している。

## 適用範囲

- **対象**　エージェントによるブランチ・worktree 操作の制御、push と PR 作成、作業の区切りごとの commit・push と、残りの検出、マージの許可条件、GitHub Ruleset の導入選択（既定 off の任意の追加事項）・権限検査・適用・整合検査、既存導入先の移行。
- **対象外**　既存のコミット履歴の書き換え、組織向け Global MCP サービスの配備、既存のプレビュー・リリース設定の変更。
- **関連する運用**　恒常的な分岐元は、リポジトリの宣言で分岐元として指定されたブランチを指す。開発ブランチとは、宣言で作業が許可され、恒常的な分岐元や保護ブランチに該当しないブランチを指す。依存作業のため一時的に分岐元に指定した開発ブランチは、引き続き開発ブランチの規則に従う。GitHub のレビュー・必須チェック・マージ権限は既存の設定と併用する。

## 要件

### 1. Claude Code と Codex で BRW を強制する

**目的**　開発者が、利用するエージェントにかかわらず同じブランチ規則で作業できるようにする。

#### 受け入れ条件

1. When 対応する Claude Code または Codex で BRW 導入済みリポジトリを操作するとき, the BRW shall 共通の宣言に基づき、対象のブランチ変更操作を実行前に判定する。
2. When エージェントが開発ブランチや作業用 worktree の作成・再開を BRW の手順を経ずに実行しようとしたとき, the BRW shall 対象操作を拒否し、利用できる BRW の手順を表示する。
3. When エージェントが恒常的な分岐元、保護ブランチ、または宣言外のブランチへ直接 commit・push しようとしたとき, the BRW shall 操作を拒否する。
4. If 対象のリポジトリ、操作、更新先を確定できないとき, then the BRW shall 規則に適合すると確認できるまで対象の変更操作を止め、判定できなかった理由を表示する。
5. Where BRW を導入していないリポジトリ, the BRW shall 通常のエージェント操作を通す。
6. When 送り先のリモートの URL が SSH の別名ホスト（`~/.ssh/config` で付けた名前）で、利用者の SSH 設定がその別名を `github.com` に解決するとき, the BRW shall その別名を GitHub のリポジトリを指す送り先として扱い、リポジトリの宣言への記載や追加の remote の設定を求めずに、判定と PR 作成・公開の処理を行う。解決は GitHub などへの通信なしで行う。
7. If 別名が `github.com` 以外に解決されるとき、解決に失敗するとき、または URL に認証情報が含まれるとき, then the BRW shall 従来どおり送り先を確定できないものとして扱い、要件 1 の 4 に従って対象の操作を止める。
8. When 送り先を確定できず操作を止める原因が、読み取れない SSH の別名ホストであると判別できるとき, the BRW shall 判定できなかった理由に、別名ホストのため読めなかったことと、とれる対処（GitHub を指す https の remote を足すなど）を含める。

### 2. 通常の push と作業完了時の PR 作成を進める

**目的**　開発者が確認を繰り返さずに、途中の作業を共有し、完了した変更のレビューを依頼できるようにする。あわせて、作業が途中で終わっても、利用者が GitHub 上で spec や変更を確認でき、リモートの作業ブランチだけで別の環境・別のエージェントが作業を再開できるようにする。

#### 受け入れ条件

1. When エージェントが登録済みの運用宣言に従い、対象の開発ブランチへ通常の push を行うとき, the BRW shall 既定で操作ごとの確認を省略する。
2. When 作業完了が確認でき、対象の開発ブランチと作業の分岐元が確定しているとき, the BRW shall 既定で追加確認なしにその作業の変更を push する。取り込み先が保護対象の場合は push の成功を確認してから対象の分岐元への PR を用意する。開発ブランチ間の取り込みのために PR は作成しない。
3. When 保護対象への公開で同じリポジトリ・取り込み元・取り込み先に一致するオープンな PR があるとき, the BRW shall その PR を再利用する。
4. When PR を用意できたとき, the BRW shall URL を報告する。
5. While 作業が途中であるか、利用者への回答が調査・確認のみである間, the BRW shall 作業完了を条件とする自動 PR 作成を保留する。
6. Where 宣言または利用者の指示が特定の push や PR 作成を制限する運用, the BRW shall 該当する制限を既定の動作より優先する。
7. If 認証・通信・権限の問題で push または PR 作成が失敗したとき, then the BRW shall 成功した処理、未完了の処理、失敗理由を報告し、再実行時に既存の PR と重複しないよう処理する。
8. When 強制 push、ブランチやタグの削除、または送り先を確定できない push が要求されたとき, the BRW shall 通常の push に対する確認省略を適用しない。
9. When spec の要件・設計・タスクのいずれかの生成が完了したとき, the BRW shall 作業ブランチ上でその変更を、利用者の許可を求めずに commit し、push する。
10. When 実装の 1 タスクが完了したとき, the BRW shall 作業ブランチ上でそのタスクの変更を、利用者の許可を求めずに commit し、push する。
11. The BRW shall 区切りごとの commit・push により、作業の途中で終了しても、リモートの作業ブランチだけで別の環境または別のエージェントが作業を再開できる状態を保つ。
12. When エージェントが応答を終えようとするとき、作業ブランチに未コミットの変更または未 push の commit があるとき, the BRW shall 応答の終了を止め、commit と push の手順を案内する。
13. While 調査・確認のみの応答で作業ブランチに未コミットの変更も未 push の commit も無い間, the BRW shall 応答の終了を止めない。
14. While 利用者の指示または宣言が当該作業の push を禁じている間, the BRW shall 区切りごとの push と、未 push を理由とする応答の終了の停止を行わず、commit までにとどめて未 push であることを報告する。
15. If 区切りの commit または push が失敗したとき, then the BRW shall 成功した処理、未完了の処理、失敗理由を報告し、変更が手元に残っていることを示す。
16. While 現在のブランチが保護ブランチ、恒常的な分岐元、または宣言外のブランチである間, the BRW shall 区切りごとの commit・push を適用せず、要件 1 の 3 に従って操作を拒否する。

### 3. 取り込み先に応じてマージと PR 作成を使い分ける

**目的**　依存する開発作業を進めながら、分岐元や保護ブランチへの反映は利用者が決められるようにする。あわせて、クラウドセッションや他のプロバイダでの作業によりリモートだけが更新されたとき、手元のブランチをリモートに追いつかせられるようにする。

#### 受け入れ条件

1. When 作業上必要な取り込みの元と先がともに宣言上の開発ブランチであり、適用されるリポジトリ規則を満たすとき, the BRW shall PR 作成や操作ごとの追加確認を求めずにローカルマージを進められるようにする。
2. When エージェントが開発ブランチ以外を対象にマージまたは自動マージ予約を試みたとき（4・5 の取り込みを除く）, the BRW shall 対応する操作経路で実行を拒否する。開発ブランチ間の取り込みはローカルマージで扱い、エージェントが GitHub の自動マージを予約する必要はない。
3. When 保護対象の分岐元への PR を用意したとき, the BRW shall 対象 PR の URL と取り込み先を利用者に示し、squash マージはリポジトリのマージ条件を満たした利用者が GitHub 上で行うよう案内する。エージェントによる操作は PR の作成または再利用までとする。
4. When エージェントが恒常的な分岐元または保護ブランチを取り込み先とし、同じ名前のリモート追跡ブランチ（`origin/main` など）を取り込み元として、履歴の分岐を作らない更新（fast-forward）だけで手元のブランチを更新するとき, the BRW shall 実行を拒否せず、宣言が登録済みであれば操作ごとの追加確認を省略できるようにする。
5. When エージェントが開発ブランチを取り込み先とし、宣言上の恒常的な分岐元または保護ブランチのリモート追跡ブランチ（`origin/main` など）を取り込み元として手元で取り込むとき, the BRW shall 実行を拒否せず、宣言が登録済みであれば操作ごとの追加確認を省略できるようにする。
6. If 4 の更新に fast-forward 以外（マージコミットの作成）が必要なとき、または取り込み元が上記以外の非開発ブランチ（手元の別ブランチ、宣言外のリモートなど）のとき, then the BRW shall 実行を拒否し、拒否の理由と、PR による反映または開発ブランチ間のローカルマージという代替手段を表示する。
7. The BRW shall 4・5 の許可の対象を取り込みに限り、`rebase` による取り込みの扱い、および分岐元・保護ブランチへの直接 commit・push の拒否（要件 1）を変更しない。

### 4. BRW 導入時に Ruleset の採否を確認する

**目的**　導入担当者が、どのリポジトリのどのブランチに GitHub 側の制限を追加するか選べるようにする。

#### 受け入れ条件

1. When BRW の新規導入、または既存導入先で Ruleset の採否が未設定の状態から移行を始めるとき, the BRW shall 対象リポジトリ、恒常的な分岐元、PR 必須・squash 限定の効果を示し、「導入しない」を既定の選択肢として利用者に選択を求める。Ruleset は既定 off の任意の追加事項であり、エージェントが自発的に提案・適用しない。
2. When 利用者が対話で既定の選択肢を確定したとき, the BRW shall Ruleset を導入しないものとして GitHub への認証・通信・書き込みなしでエージェント側の導入を進める。When 利用者が導入を明示的に選択したとき（対話で明示した導入、または `--ruleset on`）, the BRW shall 権限検査に進む。
3. If 非対話の実行で利用者が採否を指定しておらず保存済みの選択も無いとき, then the BRW shall Ruleset を導入しないものとして扱い（GitHub への認証・通信・書き込みなし）、後から導入を選択して再実行できる方法を表示する。過去の選択が読み取れないときは適用せず保留する。
4. When 利用者が Ruleset を導入しないことを選択したとき, the BRW shall その選択を記録し、GitHub 側の設定変更を省いてエージェント側の導入を進める。
5. When 同一のリポジトリと対象ブランチについて導入を再実行するとき, the BRW shall 利用者が記録した選択を引き継ぐ。
6. When 対象リポジトリまたは保護対象ブランチが変わるとき, the BRW shall 変更後の適用範囲について選択を確認する。

### 5. Ruleset の設定権限を検査し、適用を自動化する

**目的**　導入担当者が、対象リポジトリに対する権限の確認から適用後の検査までを BRW で実行できるようにする。

#### 受け入れ条件

1. When Ruleset の導入が選択されたとき, the BRW shall 設定を変更する前に、実行に使用する認証情報で対象 GitHub リポジトリの Ruleset を設定・変更できる権限があること、および対象リポジトリで必要な Ruleset を利用できることを機械的に検査する。
2. If 認証、必要な権限、Ruleset の利用可否、または対象リポジトリを確認できないとき, then the BRW shall 設定の変更を保留し、確認できなかった項目と再試行に必要な対応を表示する。
3. When 利用者が導入を選択し、事前検査を通過したとき, the BRW shall 対象ブランチに PR 必須・squash 限定の Ruleset を作成または適用する。採否の確認から適用までを一連の導入操作で進められるようにする。
4. When 適用後の有効な設定を取得したとき, the BRW shall 対象ブランチに PR 必須と squash 限定が適用されていること、squash がリポジトリで有効であること、エージェントの作業権限では制限を迂回できないことを検査する。
5. If 既存のルールとの競合、適用失敗、または適用後の検査失敗があるとき, then the BRW shall Ruleset の導入を未完了として扱い、確認済みの変更と解消すべき項目を表示する。
6. When 対象の Ruleset がすでに有効で要件を満たしているとき, the BRW shall 既存の設定を再利用し、同一の制限を重複登録せずに検査結果を報告する。
7. When Ruleset を適用するとき, the BRW shall 対象外のブランチおよび既存のレビュー・必須チェックなど他の制約を維持する。
8. Where 対象ブランチに Ruleset が有効な場合, the GitHub shall 通常の作業権限による直接 push と非 squash のマージを拒否する。

### 6. 導入状態と実際に有効な強制範囲を確認する

**目的**　運用担当者が、導入済みの設定と実際に有効な制限を確認できるようにする。

#### 受け入れ条件

1. When BRW の導入状態を検査するとき, the BRW shall エージェントごとに対象操作の強制が有効かどうかを示し、フックの未導入、未信頼、未対応の実行環境または操作経路を区別して報告する。
2. When Ruleset の導入を選択したリポジトリの整合を検査するとき, the BRW shall Ruleset の実効設定を宣言に照らして確認し、設定のずれまたは確認不能を報告する。
3. Where 旧パスに BRW の宣言だけがある既存リポジトリ, the BRW shall 既存のブランチ規則を読み込み、導入状態の検査と移行に利用できるようにする。
4. When push または PR 作成後に既存の worktree の片付けを行うとき, the BRW shall 取り込みまたは PR に関する既存の片付け条件を評価し、未コミット・未 push の変更がある worktree を保持する。
