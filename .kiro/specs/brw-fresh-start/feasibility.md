# 実現性の記録: brw-fresh-start

## 実機検証の要否

- 判定: 必要

外部の動作に依存する前提があるため「必要」とする（2026-11-28 の要件の生成時点）。設計の段階で、下の前提ごとに PoC か一次資料の根拠を確認した（「設計の確認」の節）。

| 前提 | 依存する外部の動作 | 根拠 | PoC の方針 |
|---|---|---|---|
| Claude のプラグインの最新の版を取得し、導入済みの版と比べられる（オフラインの判別を含む） | Claude Code のプラグイン・マーケットプレイスの CLI と配布元 | 設計の確認の 1 | 実環境で、取得できる場合・できない場合の出力と終了コードを確かめる |
| Claude のプラグインを更新したとき、実行中の操作・同じセッションに反映されるか（再起動が要るか） | Claude Code のプラグインの更新と読み込みの挙動 | 設計の確認の 2 | 更新の前後で、実行中の BRW とフックの版を観測する |
| Codex が参照する clone の最新との比較と、fast-forward だけの更新ができる | git の取得・更新の挙動と、Codex がその clone を参照する形 | 設計の確認の 3 | 一時リポジトリで、最新・遅れ・分岐の各状態を作って確かめる |
| 未コミットの変更がある作業ツリー（BRW 自身の開発中を含む）で、変更を失わせずに更新できるか、できないときは安全に失敗する | git の取り込みの挙動 | 設計の確認の 4 | 一時リポジトリで、追跡ファイルの変更が衝突する場合・しない場合を確かめる |
| 実行中のスクリプト自身が更新で書き換わっても、続行または中止が安全にできる | Node.js のモジュール読み込みの挙動 | 設計の確認の 5（外部の動作に依存しない設計にした） | 更新の途中で実行中のファイルを書き換えて、挙動を観測する |
| 配布元に到達できない・待ち時間を超えたことを判別できる | ネットワークと各 CLI の失敗の出力 | 設計の確認の 6 | 到達できない状態（オフライン）を再現して確かめる |

## 設計の確認

- 判定: 通過

確認日 2026-11-28（`/kiro-validate-design` で再確認）。根拠の無い前提: なし（別の提供元の再確認でも「なし」）。別の提供元のレビューを 5 回受け、指摘（共有キャッシュの選択、git の SHA の一致、子孫の打ち切り、状態の契約、期限切れ後の排他）を設計と PoC に反映した。レビューの上限（修正 2 回）に達したため、3 回目の指摘（期限切れ後の再開条件、`unchanged` の指紋）は、前者を利用者の決定（上限時間後に再チェックし、最新なら再開・古ければ手動の復旧）で、後者を設計の修正で解消した。`/kiro-validate-design` の再確認で出た契約の指摘（印の処理の流れ、`unchanged` の判定、戦略の引き渡し）は設計に反映し、最後に残った競合（印を消す直前に別の実行が新しい印を残す）も排他の中の読み直しと再チェックの規則で解消した。この最後の修正は、レビュー役の再確認を受けていない。
