子（指揮役から仕事を任される別のモデル）への分担と既定のモデルは次のとおりです（括弧内は格。モデルの強さの段階で、数字が大きいほど上位です）。
- 実装・修正は同じ提供元の子（指揮役の 1 つ下の格。指揮役が最下位なら指揮役自身）、レビューとデバッグの原因調査は別の提供元（指揮役の格以下で最上位）、調査は別の提供元（指揮役の 2 つ下の格、最低は格 1）が行います。
- 格 4 は子に使いません。どの役割も、設定の子の上限（`subagents.maxModel.<提供元>`。未設定は格 3）まで下げます。

| 指揮役 | 実装・修正 | レビュー・デバッグ | 調査 |
|---|---|---|---|
| Haiku（1） | 指揮役自身 | Luna | Luna |
| Sonnet（2） | Haiku | Terra | Luna |
| Opus（3） | Sonnet | Sol | Luna |
| Fable（4） | Opus | Sol | Terra |
| Luna（1） | 指揮役自身 | Haiku | Haiku |
| Terra（2） | Luna | Sonnet | Haiku |
| Sol（3） | Terra | Opus | Haiku |
| Astra（4） | Sol | Opus | Sonnet |

上限が Claude は Sonnet、Codex は Sol のときは、Fable の指揮役の実装が Sonnet、Sol・Astra の指揮役のレビュー・デバッグが Sonnet になります。

格と推論量（考える深さ）の選び方の目安です。
- 既定の推論量は、格 1 の子で `high`、格 2 以上の子で `medium` です（推論量の上限まで下げます）。推論量の上限は、系統ごとの上限（`subagents.maxEffort.<系統>`）、無ければ共通の上限（`subagents.maxEffort.default`）、どちらも無ければ `high` の順で求めます。
- 作業ごとに、対象のモデルが受け付ける推論量のうち上限以下から選びます。格 1 は `high` を選んでよく、格 2 以上は `medium` を基本とし、重要な作業だけ `high` にします。軽い作業は `low` でよく、特に格 3 では `low` も選択肢です。
- 複雑な調査（例: 複数のアプリケーションにまたがる関係箇所の洗い出し）は、指揮役の判断で調査役を 1 つ上の格にしてよいです。ただし指揮役の格より下、かつ子の上限以下にします。
- 上位の格ほど推論量を上げたときの費用が大きいので、格と推論量は作業の重大度と費用の釣り合いで選びます。これらは仕組みで強制しない目安です。

作業の流れです。
- 実装: 実装役の実装 → 別の提供元のレビュー 1 回 → 指摘があるときだけ、同じ実装役が修正 → 同じレビュー役が指摘箇所だけ再確認します。
- 設計: 読み取り専用の調査役が事実を集めて要約を返す → 指揮役が設計 → 別の提供元が設計をレビューします。判断を含む確認（技術の実現性の確認・PoC（試作）の検証）は調査役ではなくレビュー役に任せます。
- デバッグ: 読み取り専用の原因調査（別の提供元。別の提供元による確認を兼ねます）→ 修正（同じ提供元）→ テストで確かめます。修正の後に別のレビューを重ねない運用です。
- 結果の扱い: 指揮役は同じ観点のレビューをやり直さず、子の結果を未確認として扱い、差分と必要なテストで確かめてから完了とします。

cc-sdd の手順が「Agent ツールで子に任せる」と書く箇所は、次のように読み替えます。
- 子の起動のたびに、今の自分のモデルを渡して名前を求めます: `node .agent-hooks/cc-sdd-bootstrap/delegate.mjs --resolve-model --from claude --role implement --orchestrator-model <今の自分のモデル>`
- 出力は `<名前> <推論量>` の 1 行です。先頭の名前を `subagent_type` に入れて起動します（モデルと推論量は定義に入っています）。フックは起動の引数の `model` か定義から子のモデルを取り、起動の引数と定義のどちらにもモデルが無い起動は、未指定として拒否され、使う定義の名前を求めるコマンドが示される。
- Codex の子を起動する入口（`delegate.mjs`）は、設定 `codex.trustHooks` が false でなければ、その起動の間だけ承認の確認を省く指定（`--dangerously-bypass-hook-trust`）を付けます。指定は設定ファイルには保存されません。この Codex が指定を受け付けないときは子を起動せず案内します。
- 入口の役割は作業ごとに指定します: レビューは `--role review`、デバッグの原因調査は `--role debug`、調査は `--role investigate`（役割ごとに既定のモデルが違います。例: Sonnet の指揮役で investigate は Luna、review は Terra）。
- 別の提供元の入口の例（役割ごとに指定を変え、同じ依頼内容と成果物の形式のまま渡します）: `node .agent-hooks/cc-sdd-bootstrap/delegate.mjs --from claude --role review --orchestrator-model <今の自分のモデル> --instructions <指示のファイル>`、`node .agent-hooks/cc-sdd-bootstrap/delegate.mjs --from claude --role debug --orchestrator-model <今の自分のモデル> --instructions <指示のファイル>`、`node .agent-hooks/cc-sdd-bootstrap/delegate.mjs --from claude --role investigate --orchestrator-model <今の自分のモデル> --instructions <指示のファイル>`
- 環境変数 `CLAUDE_CODE_EFFORT_LEVEL` が設定されていると、指揮役と子の推論量がすべてその値になり、役割定義の推論量は効きません。
- 組み込みの子は起動ごとに推論量を変えられず、選んだ定義の推論量で動きます。別の推論量が要るときは同じ提供元の入口（`claude -p`）を使います: `node .agent-hooks/cc-sdd-bootstrap/delegate.mjs --from claude --role implement --to same --effort <値> --orchestrator-model <今の自分のモデル> --instructions <指示のファイル>`

別の提供元が使えないときは、すべての役割を同じ提供元の、指揮役と異なり指揮役の格以下かつ子の上限以下のモデルで行い、レビューは 1 回です。
- 名前は `node .agent-hooks/cc-sdd-bootstrap/delegate.mjs --resolve-model --from claude --role review --to same --orchestrator-model <今の自分のモデル>` のように、該当する役割（review・debug・investigate・implement）を指定して求め、出力の先頭の定義の名前（読み取り専用の定義は道具を制限済み）を `subagent_type` に入れて起動します。
- 同じ提供元に候補が無い（入口が指揮役自身で行うよう示す）ときは、その作業を指揮役が自分で行う運用です（Haiku・Luna の指揮役では別の系統が無く、入口は終了 2 を返します）。

指示のファイルと書き込みの決まりです。
- 指示のファイルは `~/.cache/cc-sdd-bootstrap-scratch/` に置きます（リポジトリ内と `/tmp` には置きません）。範囲・必要な決まり・禁止する操作・成果物の形式を書き、子が CLAUDE.md・AGENTS.md を読むことに頼らないでください。
- 書き込みは 1 つずつ行います。書き込み可の子の実行中は、読み取り専用の子も重ねない運用です。

子の起動が拒否されたときの扱いです。
- 組み込みの子の起動が利用環境の許可の判定で拒否された場合に限り、依頼の範囲・決まり・成果物の形式を依頼文に直接書いて 1 度だけ起動し直します。入口の CLI の委任は指示のファイルを標準入力に渡すので対象外です。
- それでも拒否されたら、指揮役が子の作業を代わりに進めず、拒否の状況と選べる進め方（利用者が許可する・別の提供元が使えるまで待つ・指揮役が直接進めることを利用者が認める）を示して止まります。
- 導入時に子の起動の許可は前もって与えない（許可の決まりは置かない）ものとします。
- 別の提供元（codex）の子が使えないときに、指揮役の提供元の子へ切り替えることには、利用者の許可を求めない運用です。

新機能追加系の作業（`/kiro-discovery`・`/kiro-spec-init`・`/kiro-spec-quick`・`/kiro-spec-batch`・`/kiro-impl`）を始める前に、作業用ブランチへ移ってください。

基底ブランチ（既定は `main`・`master`・`develop`）の上では、新しい作業を始めないでください。既存の作業用ブランチがあればそこへ、無ければ新しく作ってそこへ移ってください。どのブランチを使えばよいか分からなければ、利用者に尋ねてください。ブランチを作れないときは、その理由を利用者に伝えて作業を止めてください。

フックが有効なら、基底ブランチの上での作業はフックが拒否することがあります（入力ごとに最大 2 回。ブランチの作成・切り替えを試みた後と、ブランチを判定できないときは拒否しません）。拒否の理由に従って作業用ブランチへ移ってから続けてください。フックが拒否しなくても、この運用を守ってください。手順書を読むことは、ブランチに関係なくできます。

`/kiro-validate-impl` の検証が GO になったら、作業ブランチを push して PR を作ってください。NO-GO などの場合は PR を作らず、結果を報告してください。基底ブランチの上にいるときは、PR を求めません。

PR の作成は設定の既定の運用であり、利用者が事前に求めたものとして扱ってください。その場で確認を求めないでください。PR のタイトルと本文は、作業の内容から作ってください。フックが有効でも、PR が無いと判定できたときだけ止まります（1 回）。基底ブランチの上、PR の有無を判定できないとき（`gh` が無い・未認証など）、PR が既にあるとき、設定が無効のときは止まりません。

2 つの流れは、設定ファイル `.cc-sdd-bootstrap.json` の `workflow.branchGate`（作業前のブランチ確保）と `workflow.prAfterValidate`（検証後の PR）で、それぞれ無効にできます（真偽値。既定は有効）。基底ブランチの一覧は `workflow.baseBranches`（カンマ区切り。既定は `main,master,develop`）で変えられます。

要件の段階（`/kiro-spec-requirements`）では、その spec が実機検証を必要とするかを判定してください。外部の動作（ツール・API・OS・ネットワーク・第三者のツールの挙動）に依存する前提が 1 つでもあれば「必要」、そのような前提が 1 つも無いときに限って「不要」にできます。必要なら、前提ごとに PoC（実機で前提を確かめる試作。結果は PoC 文書に残す）を作ることを基本とし、PoC を作らない前提は、前提と理由を記録してください。必要でも不要でも、判定と理由を記録に残してください。

設計（`/kiro-spec-design`・`/kiro-validate-design`）とタスク計画（`/kiro-spec-tasks`）の承認の前に、前提ごとに根拠を確認し、結果を記録に残してください。認める根拠は、一次資料（出典の場所と版が示せるもの）か、PoC 文書（`.kiro/specs/<spec 名>/poc/<段階>_<通し番号>.md`。位置付けと結果が文書で追えるもの）です。根拠の無い前提は「未確認」として残し、承認の前に根拠を足してください。

PoC 文書は、その PoC が根拠になる spec のディレクトリの中の `poc/<段階>_<通し番号>.md` に置きます。`<段階>` は `requirements`・`design`・`tasks`・`impl` のいずれか、`<通し番号>` は段階ごとに 01 から始まる 2 桁です。追加は同じ段階の最大の番号の次にし、取り除いた番号は詰めません。通し番号は要件・設計の番号とは対応させず（要件や設計の番号は改訂でずれるため）、対応は文書の `- 対象:` に書きます。同じ前提を別の段階でもう一度確かめるときは、新しい番号の文書を作り、前の文書は書き換えません。複数の spec が同じ PoC を根拠にするときは、1 つの spec のディレクトリにだけ置き、ほかの spec の記録からは相対パス（例: `../<spec 名>/poc/design_01.md`）で指します。実現性の記録の根拠の表では、PoC を根拠にする前提の出典の欄に、その PoC 文書を記録からの相対パス（例: `poc/design_01.md`）で挙げてください。

PoC 文書の冒頭に `- 対象: <確かめた前提と、関係する要件・設計の番号>` と `- 段階: <段階>` の 2 行を書き、続けて、実施内容の要点（数行）、実施日、環境と版（確かめた外部のツールの版を含む）、結果と仕様への反映、確かめられなかったこと（あれば）を書いてください。実施の結果が前提と食い違ったときは、その食い違いと、仕様をどう直したかも書いてください。見出しは自由です。再現できるだけの詳しさ、スクリプトの全文、コマンドの完全な列挙は求めません。必須の項目が欠けた PoC 文書は根拠として認められず、その前提は「未確認」になります。

PoC のスクリプト・入力・出力は、リポジトリの管理対象の外の一時ディレクトリ（`mktemp -d` など）で使い、管理対象に残しません。PoC の前後で、PoC 文書の追加と、その spec の実現性の記録の更新を除き、管理対象が変わらないようにしてください。管理対象の中にファイルを作ってしまったら、確認の後に取り除いてください。

実機検証が必要な spec は、実際の配置物・実機を使う確認を、タスク計画の最初の実装タスク（群）に置いてください。最後に置いたり欠けていたりするときは、「未解決」として記録し、計画を直してください。

記録は `.kiro/specs/<spec 名>/feasibility.md` に置きます。3 つの節 `## 実機検証の要否`・`## 設計の確認`・`## タスク計画の確認` があり、各節に `- 判定: <語>` の行をちょうど 1 つ書きます。要否の語は `必要`・`不要`、段階の語は `通過`・`未通過` です。判定の行より前に水平線（`---`）を置かないでください。やり直したら、該当節の判定をまず `未通過` に戻してから更新してください。cc-sdd のファイル（spec.json・requirements.md・design.md・tasks.md）には印を足さないでください。

レビュー役（子のエージェント）を起動するときは、依頼文に実現性の観点（前提ごとの根拠が一次資料か、PoC 文書で位置付けと結果が追える PoC で確かめられているか）を入れてください。

実装中に要件・設計と現実の食い違いが見つかったら、requirements.md・design.md をその場で書き換えず、cc-sdd の Blocked の扱いで該当する段階へ戻してください。戻した後は、記録の該当節を更新し直してください。

フックが有効なら、設計の確認が `通過` でない spec の `/kiro-spec-tasks`、名前つきの `/kiro-spec-quick`・`/kiro-spec-batch`、タスク計画の確認が `通過` でない spec の `/kiro-impl` の入力は、記録の判定が条件を満たさないとき止まります。止めたときは、止めた入力・止めた理由・次にやることが、応答の文章で示されます（画面に何も出ないまま止まることはありません）。通す手順は、該当する段階の確認を済ませ、記録の `- 判定:` を `通過` にして、同じ入力をもう一度送ることです。実機検証が不要なら、`## 実機検証の要否` に `- 判定: 不要` と理由を書いてください。spec を特定できない入力は止まりません。名前なしの `/kiro-spec-batch` は止められないので、spec ごとに個別の段階のコマンドで確認してください。

フックの信頼が承認されていない環境などでフックが動かなくても、この運用を文章で守ってください。フックは入力を止めるだけで、運用の決まりはこの文章が定めます。
